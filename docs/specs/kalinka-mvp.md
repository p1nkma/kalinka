# Спецификация: Kalinka MVP (Калинка)

## 1. Назначение продукта
**«Калинка» (Kalinka)** — самостоятельная бесплатная open-source платформа для онлайн-бронирования встреч, встреч один на один и групповых событий. Продукт создается на базе форка открытого ядра `calcom/cal.diy` (лицензия MIT). Проект нацелен на развитие русскоязычного и глобального open-source сообщества, предоставление альтернативы проприетарным сервисам (calink.ru, Calendly, Cal.com SaaS) без абонентской платы и навязчивых ограничений.

## 2. Границы MVP и норматив
- **Норматив реализации**: 1 рабочий день.
- **Главный инженерный принцип**: Минимальные изменения исходного кода при 100% сохранении стабильности и функциональности upstream-ядра.

### Входит в MVP (Scope):
1. **GitHub Repository**:
   - Настоящий публичный fork `calcom/cal.diy` (`git@github.com:p1nkma/kalinka.git`).
   - Сохранена полная Git-история коммитов и связь с upstream (`upstream` remote).
   - Лицензия MIT сохранена в полном объеме с сохранением копирайтов оригинальных авторов.
   - Фиксация базового коммита: `ef7954d16ab50882ca2f263c551537115b8a8bb1`.
   - Актуальный `README.md` с описанием проекта «Калинка», инструкцией по установке и запуску через Docker.
2. **Брендинг и айдентика (Утверждён Concept 2 — Editorial Wordmark)**:
   - Название продукта в UI: «Калинка» / **Kalinka**.
   - Стиль: **New Folk Editorial** — современная технологическая платформа планирования со славянской графической культурой.
   - **Основная иконка**: Тёмно-графитовый сквиркл (`#212226`), засечковая монограмма K цвета слоновой кости (`#F6EFE4`), веточка калины с 7 глянцевыми ягодами (`#C23636`) и строго симметричным вышивальным орнаментом.
   - **Горизонтальный логотип (Concept 2)**:
     - **Primary Editorial Logo**: Монограмма K слева + выразительная каллиграфическая надпись «alinka» справа с росчерком и подстрочником `OPEN-SOURCE SCHEDULING PLATFORM` (для README, обложек, лендинга).
     - **Compact UI Logo**: Адаптированная версия для TopNav, модалок авторизации и мобильного интерфейса (монограмма + надпись, без подстрочника и волосяных линий, идеальная читаемость при 18–40 px).
     - Светлая версия: чёрная монограмма `#1A1A1B`, красная надпись `#C23636`.
     - Тёмная версия: слоновая кость `#F6EFE4`, красные ягоды и вышивка `#C23636` (без CSS-инверсии `dark:invert`).
   - Комплект фавиконов и иконок приложения: `favicon.ico`, `favicon-16x16.png`, `favicon-32x32.png`, `apple-touch-icon.png` (180×180 solid `#212226` с безопасной зоной iOS), `site.webmanifest`.
   - Локализованные тексты для RU и EN интерфейса.
3. **Сборка и Docker-образ**:
   - Собственная сборка Docker-образа из исходного кода форка (`Dockerfile`), содержащая измененные ресурсы и конфигурации.
   - Запуск через Docker Compose (PostgreSQL + Redis + Kalinka Web).
4. **Инфраструктура и домен**:
   - Развертывание на Linux VPS.
   - Подключение домена `ka-linka.ru` через Timeweb DNS (A-запись).
   - Reverse-proxy (Caddy) с автоматическим получением и обновлением SSL-сертификатов (Let's Encrypt HTTPS).
   - Изоляция внутренних сервисов: PostgreSQL и Redis доступны только внутри внутренней Docker-сети `stack`, внешние порты закрыты.
5. **Функциональный сценарий (Smoke Verification)**:
   - Создание учетной записи первого администратора через `/auth/setup`.
   - Создание и настройка типа события (Event Type: 15/30/60 минут, очная встреча / звонок / внешняя ссылка).
   - Настройка графика доступности (слоты времени, таймзона).
   - Бронирование слота гостем в инкогнито-сессии без авторизации.
   - Отображение созданной брони в личном кабинете организатора.
   - Проверка персистентности данных после рестарта контейнеров (`docker compose restart`).

### НЕ входит в MVP (Out of Scope):
- Переписывание архитектуры monorepo или переход на другие фреймворки.
- Разработка собственной системы календарей с нуля.
- Интеграция с Яндекс.Календарем, Mail.ru, Telegram-ботами (вынесено в следующие релизы).
- Платёжные шлюзы (ЮKassa, Robokassa, Stripe) и биллинг.
- Переработка системы авторизации NextAuth.
- Изменение Prisma-схемы или структуры таблиц базы данных.
- Полная переверстка фронтенда и мобильные приложения.

## 3. Проверенная архитектура исходного приложения (Cal.diy)

1. **Monorepo и пакетный менеджер**:
   - Монорепозиторий под управлением **Turborepo 2.7.1** и **Yarn Berry 4.12.0** (`.yarnrc.yml`, `node_modules` linker).
   - Node.js runtime: v22+ (в Dockerfile используется `node:22`).
2. **Приложения (`apps/`)**:
   - `apps/web`: Основное веб-приложение на **Next.js 16** (гибрид Pages Router для legacy/API и App Router `app/(use-page-wrapper)` + `app/(booking-page-wrapper)`).
   - `apps/api/v2`: REST API v2 (опциональный микросервис, для базового веб-интерфейса и бронирования не обязателен, так как web использует собственный tRPC).
3. **Ключевые пакеты (`packages/`)**:
   - `packages/prisma`: ORM Prisma 6.16.1, Kysely, схема PostgreSQL (`packages/prisma/schema.prisma`), 597 миграций.
   - `packages/trpc`: Маршрутизаторы tRPC для связи фронтенда `apps/web` с базой данных и сервисами.
   - `packages/features`: Модули бизнес-логики (`auth`, `bookings`, `eventtypes`, `availability`, `schedules`, `users`).
   - `packages/ui`: Библиотека React-компонентов, Radix UI, логотипы, диалоги, формы.
   - `packages/config/theme`: Токены темы (`tokens.css`), Tailwind CSS v4 конфигурация.
   - `packages/i18n`: Интернационализация (40+ языков, включая полный русский перевод в `locales/ru/common.json`).
   - `packages/lib`: Константы приложения (`constants.ts`), утилиты форматирования, валидация.
4. **Хранилище данных**:
   - **PostgreSQL**: Хранение пользователей, профилей, типов событий, расписаний доступности, бронирований.
   - **Redis**: Кэширование доступных слотов и сессий.
5. **Жизненный цикл Docker**:
   - Многоэтапный `Dockerfile` (`builder` -> `builder-two` -> `runner`).
   - При сборке компилируются embed-компоненты, tRPC и Next.js (`yarn workspace @calcom/web run build`).
   - Статические URL при сборке заменяются плейсхолдером `http://NEXT_PUBLIC_WEBAPP_URL_PLACEHOLDER`.
   - На этапе старта контейнера (`scripts/start.sh`):
     1. `scripts/replace-placeholder.sh` заменяет плейсхолдер на реальный `NEXT_PUBLIC_WEBAPP_URL`.
     2. `scripts/wait-for-it.sh` ждет готовности базы данных.
     3. `npx prisma migrate deploy` применяет миграции к PostgreSQL.
     4. `npx ts-node --transpile-only /calcom/scripts/seed-app-store.ts` инициализирует доступные приложения.
     5. `yarn start` запускает веб-сервер на порту 3000.

     - Безопасные учетные данные PostgreSQL.

## 5. Требования к инфраструктуре

- **Сервер**: Linux VPS (Ubuntu 22.04 / 24.04 LTS), минимум 2 vCPU, 4–8 GB RAM (для комфортной сборки Next.js с Turborepo выделяется swap 4GB, если RAM < 8GB), 30+ GB SSD.
- **Стек контейнеризации**:
  - Docker Engine 24+
  - Docker Compose v2.20+
- **Сетевой периметр**:
  - Порты 80 (HTTP) и 443 (HTTPS) открыты для Caddy.
  - Порт 22 (SSH) для административного доступа.
  - Порты PostgreSQL (5432) и Redis (6379) строго изолированы во внутренней Docker-сети `stack` (`127.0.0.1` или no host binding).
- **DNS**:
  - Регистратор/DNS: Timeweb DNS.
  - A-запись: `ka-linka.ru` -> IP-адрес VPS.
  - A-запись (опционально): `www.ka-linka.ru` -> IP-адрес VPS.

## 6. Основные технические риски и их предотвращение

| Риск | Описание | Мера предотвращения |
|---|---|---|
| **OOM при сборке Docker** | `next build` и генерация tRPC требуют значительного объема RAM (> 4-6 GB). При недостатке памяти процесс убивается OOM Killer. | В `Dockerfile` передается `NODE_OPTIONS=--max-old-space-size=6144`. На сервере настраивается swap-файл (4-8 GB) перед первой сборкой. |
| **Уязвимость дефолтных секретов** | `NEXTAUTH_SECRET=secret` и `CALENDSO_ENCRYPTION_KEY=secret` позволяют подделать сессионный токен и расшифровать БД. | Обязательная генерация случайных 32-байтных токенов через `openssl rand -base64 32` в production `.env`. Дефолтные значения заблокированы. |
| **Перехват аккаунта администратора** | Роут `/auth/setup` позволяет зарегистрировать первого админа без подтверждения почты, если `userCount === 0`. | Первоначальный setup выполняется администратором сразу после старта контейнера, либо порт защищается базовой авторизацией / временным файрволом до завершения setup. |
| **Конфликт портов** | `calcom-api` в `docker-compose.yml` по умолчанию биндится на порт 80, конфликтуя с Nginx/Caddy. | Порт `calcom-api` отключается или меняется на внутренний, веб-интерфейс работает через встроенный tRPC на порту 3000. |
| **Сломанные плейсхолдеры URL** | Next.js кэширует `NEXT_PUBLIC_WEBAPP_URL` при сборке. Если `replace-placeholder.sh` не отработает, ссылки будут вести на плейсхолдер. | Сохраняется архитектура с `replace-placeholder.sh` в `Dockerfile` и `start.sh`, проверяется финальный bundle. |

## 7. Критерии приёмки (Acceptance Criteria)

1. **GitHub**:
   - Публичный форк `https://github.com/p1nkma/kalinka` активен, имеет upstream `calcom/cal.diy`.
   - Полная история коммитов сохранена. Лицензия MIT сохранена.
   - Изменения оформлены понятными атомарными коммитами.
   - `README.md` описывает запуск и архитектуру проекта «Калинка».
2. **Брендинг**:
   - В UI отображается имя «Калинка» / «Kalinka».
   - Установлены фавиконы и логотипы Concept 2 - New Folk Editorial.
   - Базовый акцентный цвет - красный калины (`#C23636`).
   - Метаданные страниц (`<title>`, `<meta property="og:title">`) содержат бренд Kalinka.
3. **Build**:
   - Успешная сборка собственного Docker-образа `docker build -t kalinka:latest .`.
   - Контейнеры запускаются через `docker compose up -d` без падений.
4. **Deployment**:
   - `https://ka-linka.ru` отдает статус 200 OK с валидным SSL-сертификатом Let's Encrypt.
   - Редирект с HTTP на HTTPS работает корректно.
   - База данных и служебные сервисы недоступны снаружи.
5. **Functional Smoke Tests**:
   - Зарегистрирован пользователь / админ.
   - Создан тип встречи (например, «Консультация 30 мин»).
   - Настроено расписание слотов.
   - В отдельном браузере (инкогнито) открывается публичная страница `https://ka-linka.ru/{username}/{event-slug}`.
   - Успешно оформлено бронирование слота.
   - Бронирование появилось в панели организатора во вкладке «Бронирования».
   - После выполнения команды `docker compose restart` данные сохраняются в БД.
